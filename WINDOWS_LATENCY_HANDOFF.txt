Observed cause and current confidence
The long-lived Windows tray-app engine is slow even with its model warm.
Three real user dictations before intervention:
audio 2.578 / 2.642 / 2.365 seconds; key-up-to-paste 2997 / 1954 / 2243 ms.
Model acquisition: 10.16 / 21.33 / 10.79 ms; all modelWasWarm=true.
Only the engine process's execution QoS was changed to explicit HighQoS;
no model reload, app restart or setting change occurred.
Three real user dictations afterward:
audio 1.554 / 1.703 / 1.661 seconds; key-up-to-paste 411 / 330 / 274 ms.
User independently reported faster response. Post-change clips are shorter,
so the ratio is not a controlled exact speedup estimate.

Controlled lab test: identical 7.56-second Swedish fixture, model resident,
15 seconds idle before each request, original installed native ARM64 host:
system QoS: 436 / 362 ms; explicit HighQoS: 415 / 345 ms;
explicit EcoQoS: 2791 / 5768 ms. Same decoded text in every case.
Normal process priority and unrestricted 12-core affinity were observed.
GetProcessInformation reported no explicit QoS override in the original app
or host (ControlMask=0/StateMask=0); that does not reveal the effective heuristic
QoS tier. Microsoft documents visibility-based background QoS on battery.
The intervention and controlled reproduction strongly support background
power scheduling as the latency cause; no kernel trace was collected to name
the exact internal heuristic tier of the original long-lived process.
