## Writer and synchronization semantics

- In `tests/support/fake_engine_host.rs:126-136`, `log(op, id)` opens `FAKE_LOG` with create+append and writes `{op} {id}\n` using `writeln!`. It does not explicitly flush or sync; the local `File` drops on return. Each fake-host request is handled synchronously by its stdin loop: after successful decode, `main` calls `log(op.name(), id)` immediately before `handle(&host, id, op)` (`fake_engine_host.rs:168-188`, especially 185-187). Thus line order reflects the fake host's decoded-request order, not completion order. The record is made before request handling/admission.
- For window requests, the decoded request includes `priority`; `handle` then queues a job with a rank and starts `run_window` (`fake_engine_host.rs:279-284, 335-357`). The fake host acquires a slot inside `run_window` (`fake_engine_host.rs:422-440`), waits for its delay (`465-480`), and only then writes the result (`504-512`). The current log therefore indicates receipt/dispatch, not slot acquisition or completion.
- `transcribe_file_samples` defaults to batch priority and `transcribe_dictation` supplies interactive priority (`engine_host/pipeline.rs:432-440`, `414-429`). `submit_window` acquires the local slot and calls `proc.send(&window_op(req))` at `engine_host/client.rs:537-595`, with priority copied into the wire op at 700-714.
- `HostProcess::send` registers/encodes a request and queues its writer job (`engine_host/process.rs:296-317`). The writer thread performs `write_all` and `flush`, then signals completion via `job.done` (`process.rs:491-504`); `send` returns its `Pending` only after receiving that successful write result (`process.rs:318-350`). This is client-side write completion. It is distinct from fake-host decode/log receipt and from transcription response completion.
