Sagascript / Pianissimo on Windows ARM64 — local evaluation, 2026-11-01

Outcome
The ordinary dictation slowdown was strongly linked to Windows CPU scheduling/
power QoS, not repeated model loading. The scoped CPU fix is installed with the
owner's explicit approval and verified through CLI, GUI timing and idle readback.
For the tested implementations, the shipped INT8 CPU model remains the fastest
working path. Full audio-to-text runs also succeeded on Adreno GPU and Hexagon
NPU. Neither proves the performance ceiling of the hardware or future exports.

Machine and method
Snapdragon X Elite X1E78100, 12 cores, 32 GB; Adreno X1-85 driver31.0.112.0;
Hexagon driver30.0.143.0; Windows11 ARM64 build26200. Balanced/on battery for
the recorded evaluation. No global power-plan or driver changes. Background
activity and thermal state were not experimentally controlled. No energy meter
was used, so battery savings/cost cannot be calculated from these timings.

Public corpus: 11 Swedish clips, 135.54 seconds, 235 reference words. Existing
7.56s Hongkong fixture plus ten Google FLEURS dev clips, five male/five female.
Small read-speech sample, not a meeting, conversational benchmark or an English
evaluation. No private audio was uploaded. WER uses lowercase word tokens,
ignores punctuation, and does not normalize numbers or Swedish compounds.
Quality counts one observation per clip, not one per repeat. Warm medians use
iteration>0. Typical runs repeat each clip twice; shipped baseline uses three.
Different host versions, FP16/INT8 models and Python/Rust paths mean this is a
comparison of working implementations, not isolated measurements of chip speed.

GPU: what works and what failed
DirectML native ARM64, WinML2.5.96 / ORT1.28.3. Original export failed with
rank-five attention matrix multiplication. Rewriting72 attention MatMuls to
rank-three with explicit broadcasting/reshape made full ASR work. CPU parity
for transformed versus original models was independently verified on11clips.
Dynamic FP16 profile: executed DML2559 unique nodes and CPU2264 unique nodes.
INT8: DML2799 / CPU2264. Counts are not percentages of compute or wall time.
Decoder and preprocessing remain on CPU. INT8 export does not translate to
fast accelerator-native integer execution merely by selecting DirectML.

then full-corpus quality checks before any performance claim or integration.

NPU: what works and what failed
Python3.13 ARM64 / ORT1.29.0 / QNN plugin2.7.0; HTP burst mode.
Original dynamic INT8 graph rejected unsupported quantization/other operators
under strict NPU placement. FP16 fixed2048 works as3QNN partitions plus72CPU
nodes. It is hybrid inference, not100% NPU. First compile74-77s and roughly
7.8-9.3GB peak RSS. Context cache cuts encoder load to2.2-2.7s and inference
RSS to~1.43GB; cache artifact is~1.22GB. Cache and uncached outputs matched.
FP16 fixed2048 NPU~1.06s versus matched CPU FP16~1.23s: NPU has a measured
advantage in that particular comparison, but loses to shipped CPU INT8~0.39s.
Fixed758 fixture warm~0.98s; fixed3008 crashed with native0xC0000005 during
load. Therefore current prototype cannot support the full30s window robustly.
Production would need shorter-window/chunk routing, validated overlap/text
merging, cache lifecycle/versioning and CPU fallback; none was installed.

QDQ experiment
Separate five public calibration sentences were selected excluding evaluation
filenames, normalized reference text and duplicate calibration sentence IDs.
Requested uint16 activations / uint8 per-channel weights using ORT's QNN
quantizer. First failure: FP16-to-FP32 optimization crossed2GB protobuf limit.
Process-local external-initializer workaround got past preprocessing. Next
attempt reached8316MB sampled RSS after251s and was stopped by an8GB guard.
Final attempt qdq-final-bounded allowed11GB process RSS, retained3GB minimum
available system RAM and a420s time limit. It was stopped after310.37s by the
system-memory-reserve guard, peak sampled process RSS9499.60MB, exit1. No
validated QDQ output was produced. All evaluation children have terminated.
No validated QDQ accuracy, NPU latency or energy result exists at this stage.
Do not present this export failure as proof quantized NPU cannot outperform CPU.
Next export work needs a memory-bounded preprocessing/calibration/quantization
pipeline (external weights and fewer simultaneous model copies), or an approved
machine with more available RAM. Then validate QNN operator placement, held-out
accuracy and complete ASR latency. Merely raising process priority cannot solve
this export-memory problem. No additional export retries are left running.

Practical decision
Use the scoped-QoS CPU INT8 engine for current Windows dictation. Current GPU
and NPU prototypes add packaging, conversion and validation work without a
measured latency benefit over that path. GPU needs static-graph correctness
work; NPU needs a deployable quantized export plus robust window/cache handling.
Potential battery or future quantized-model benefits remain unmeasured. There
is no evidence for a guaranteed speedup figure for those unfinished designs.
